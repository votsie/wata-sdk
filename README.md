# WATA SDK

Клиентские библиотеки для платёжной системы [wata.pro](https://wata.pro) на пяти
языках: **Node/TypeScript, Python, Go, Java, .NET**.

Покрывают публичный API эквайринга (H2H) и API цифровых товаров: Steam,
Telegram Stars, пополнения игр и ваучеры.

| Язык | Каталог | Пакет |
|---|---|---|
| Node / TypeScript | [`node/`](node) | `@wata/sdk` |
| Python | [`python/`](python) | `wata` |
| Go | [`go/`](go) | `github.com/votsie/wata-sdk/go` |
| Java | [`java/`](java) | `pro.wata:wata-sdk` |
| .NET | [`dotnet/`](dotnet) | `Wata.Sdk` |

## Главное, что нужно понять до начала

**Токен WATA выпускается на терминал, а не на аккаунт.** Терминал не передаётся
в запросах — сервер определяет его по токену.

**Stars и Steam всегда живут на отдельных терминалах.** Это свойство платформы,
а не рекомендация: вызвать Stars токеном Steam невозможно, сервер откажет.

Поэтому все SDK устроены одинаково: клиент принимает **набор токенов по
продуктам**, и обращение к продукту без его токена падает с понятной ошибкой
ещё до сетевого вызова.

```ts
const wata = new WataClient({
  acquiring: process.env.WATA_ACQUIRING_TOKEN,
  stars:     process.env.WATA_STARS_TOKEN,
  steam:     process.env.WATA_STEAM_TOKEN,
});

// Ошибка конфигурации, а не загадочный 403 от сервера:
await wata.vouchers.catalog(); // токен ваучеров не задан
```

Если один терминал совмещает несколько продуктов — передайте один и тот же
токен в несколько полей. Это осознанное решение интегратора, SDK его не угадывает.

## Что внутри каждого SDK

- Полный API эквайринга: платёжные ссылки, транзакции, возвраты, баланс,
  прямая оплата по СБП, T-Pay и картой
- Полный API цифровых товаров: Steam, Telegram Stars, Top-Up, ваучеры,
  депозитный баланс — в обоих режимах оплаты (покупателем и с депозита)
- **Проверка подписи вебхуков** — SHA512withRSA по сырому телу, с загрузкой
  и кэшированием публичного ключа по окружениям
- Типизированные ошибки с кодами WATA (`PL_*`, `TRA_*`, `ORD_*`, `STM_*`, `STR_*`)
- Ретраи с экспоненциальной задержкой, таймауты, обработка `429`
- Курсорная пагинация транзакций через итератор — вручную её легко сломать
- Тесты без сети и рабочие примеры

## Подводные камни, заложенные в SDK

Эти вещи стоили времени при интеграции, поэтому вынесены в поведение библиотек:

- **Подпись вебхука — SHA-512, а не SHA-256.** Реализация с SHA-256 молча
  отвергает все подлинные уведомления.
- **Проверять нужно сырое тело.** Разобранный и собранный заново JSON меняет
  порядок ключей, и подпись перестаёт сходиться.
- **У песочницы свой публичный ключ.** Ключ, закэшированный в бою, в песочнице
  не подойдёт.
- **Баланс принимает только сегодняшнюю или вчерашнюю дату** по UTC. SDK
  проверяет это локально, не тратя сетевой запрос.
- **Курсорная пагинация требует трёх полей**, а не одного: `CursorId`,
  `CursorAmount` и `CursorDate`. Пропуск последнего ломает вторую страницу.
- **Комиссия называется по-разному**: `commission` в вебхуке и `totalCommission`
  в ответе на запрос транзакции.
- **Предоплатный вебхук требует ответа за 10 секунд**, иначе транзакция
  отклоняется без обращения в банк.
- **Заказы Telegram Stars могут попасть в статус `Review`** и не выполняются,
  пока их явно не подтвердят.
- **Изменяющие запросы не повторяются автоматически** — повтор создал бы второй
  платёж.
